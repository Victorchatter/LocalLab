# LocalLab — Bug Audit & Feature Proposals (2026-08-07)

Scope note on methodology: this session's GitHub access is scoped to
`victorchatter/locallab` only, and the ten tool codebases each live in their
own separate repo (`AgentVCR`, `Tokenauditor`, `toolcall-linter`, etc.) that
this session cannot read or clone. So this audit is two different kinds of
work stitched together:

- **`locallab` umbrella CLI** (this repo) — audited against the actual code.
  Three bugs below were reproduced, fixed, and re-verified in this session.
- **The other nine tools** — audited against their published design (READMEs,
  `PROJECTS.md`, `FEATURESv1.md` feature-tier prompts). These are risk-based
  findings aimed at the specific mechanisms each tool describes for itself,
  not line-level bug reports. Treat them as "here's what to check first,"
  and confirm against the real source in each tool's own repo.

---

## 0. `locallab` umbrella CLI — verified, fixed this session

### Bug: `selfcheck.py` fails on Linux/macOS out of the box

`_write_fake_tool()` created fake tool executables named `agent-vcr.py` and
added their directory to `PATH`, then asserted `locallab versions` found
them. But `shutil.which("agent-vcr")` only matches the *exact* filename on
POSIX — it doesn't try `.py` the way Windows PATHEXT lookup does. Every
`_run_tool()` call fell through to the `python -m agent_vcr` fallback (no
such module), so every tool showed `not installed` and the whole selfcheck
failed:

```
$ python3 selfcheck.py
selfcheck FAIL: expected version in output:
tool                       version
...
agent-vcr                  not installed
...
```

The comment in the code ("On Unix the same works when the file is
executable, and the `.py` extension is harmless") was simply wrong. Since
there's no `.github/workflows` in this repo, nothing was catching this —
the repo's own local verification story was broken.

**Fix applied:** `_write_fake_tool()` / `_write_fake_tool_subcommand()` now
write the fake executable as `{name}` (no extension, `chmod 755`, shebang
line) on POSIX and keep `{name}.py` on Windows, matching how
`_tool_command()` in `cli.py` actually resolves executables on each
platform. `python3 selfcheck.py` now passes.

**Suggested follow-up feature:** add a `.github/workflows/selfcheck.yml`
to this repo (per Tier 4 of `FEATURESv1.md`, which added this for the
individual tools but not for the umbrella itself) so a regression like this
fails CI instead of only being caught by someone happening to run
`selfcheck.py` locally on Linux.

### Bug: `locallab pipeline` never creates the `{output}` directory

`pipeline.run()` computes `output_dir = Path(recipe_dir) / f"pipeline-output-{timestamp}"`
and exposes it to steps as `{output}`, but never calls `mkdir()` on it. Both
bundled example recipes write their *first* output there:

```yaml
# locallab/recipes/record-audit-lint.yaml
steps:
  - run: agent-vcr record -o {output}/tape.jsonl -- {agent_cmd}
```

If the invoked tool opens `{output}/tape.jsonl` for writing without first
creating parent directories itself (a reasonable assumption for a CLI that
doesn't know it's being driven by a pipeline), this fails on a fresh run —
which is the primary documented use case for the pipeline feature. The
`--dry-run` path never exercises this because it only prints the resolved
command; `selfcheck.py`'s `check_pipeline_assertion()` also didn't catch it
because it wrote its fixture JSON directly into `recipe_dir`, not under
`{output}`.

**Fix applied:** `run()` now does `output_dir.mkdir(parents=True, exist_ok=True)`
before executing steps (skipped in `--dry-run`, since nothing is written
there). Verified end-to-end with a recipe whose first step writes into
`{output}/result.json`.

**Suggested follow-up feature:** extend `selfcheck.py`'s pipeline checks to
do one non-dry-run pass through a recipe that writes into `{output}`, so
this class of bug can't silently return.

### Bug: an `assert` step with a missing JSON key crashes with a raw traceback

`_eval_jq()` raises a bare `KeyError` (or `IndexError`) when a `.field`
expression references a key that isn't present in the asserted file. `run()`
didn't catch this, so instead of the documented `exit code 2` for a usage
error, a typo'd or renamed field in an `assert.jq` expression produced a
full Python traceback to the user:

```
$ locallab pipeline recipe.yaml
Traceback (most recent call last):
  ...
  File "locallab/pipeline.py", line 97, in _eval_jq
    current = current[key]
KeyError: 'missing_key'
```

This is exactly the kind of failure a pipeline recipe author hits constantly
while iterating on `jq` expressions (a field gets renamed upstream, e.g. by
a `tokenauditor` flag change), and it's much worse UX than the clean
`ASSERTION FAILED` message the tool already produces for a *value* mismatch.

**Fix applied:** wrapped the `_eval_jq()` call in `run()`'s assert branch in
a `try/except` over `(KeyError, IndexError, TypeError, ValueError,
RuntimeError)`, printing `error: step N cannot evaluate jq '<expr>': <detail>`
and returning exit code `2`, consistent with the tool's other usage-error
paths. Verified: the same recipe that used to crash now exits `2` with a
one-line message.

**Suggested follow-up feature:** `locallab pipeline <recipe.yaml> --lint`
that resolves and type-checks every `assert.jq` expression against the
recipe's declared steps' `-o` outputs (where staticaly inferable) *before*
running anything, so a bad expression is caught pre-flight.

### Other things worth a look (not fixed — lower confidence / lower severity)
- `_tool_command()`'s fallback (`python -m tool_name.replace("-", "_")`)
  assumes the installed console script's underlying package import name is
  a straight underscore-for-dash swap of the CLI name. Worth confirming this
  actually holds for all ten tools' `pyproject.toml` package layouts —
  otherwise `versions`/`doctor` report "not installed" for a tool that *is*
  installed but just not currently on `PATH` (e.g. a `pipx` shim collision).
- `cmd_update()` decides "not installed, skip" by checking for the substring
  `"not installed"` in `pipx upgrade`'s stderr/stdout. This is a reasonable
  pragmatic choice but is coupled to `pipx`'s current wording; a `pipx`
  version bump that rephrases this message would silently turn "skip" into
  "failed."
- `_eval_jq()`'s comparison regex (`(.+?)\s*(==|!=|<=|>=|<|>)\s*(.+)$`) will
  misparse an expression if the *left*-hand side legitimately contains a
  comparison-like character before the real operator. Unlikely in practice
  given the tool's simple `.key.nested` grammar, but worth a unit test with
  a right-hand string literal containing `<`/`>`.

## 1. `agent-vcr` — record/replay with tools stubbed

**Risk areas to check:**
- **Secret leakage in tapes.** The recorder sits at the wire level for both
  model APIs and MCP tool calls, so a tape is, by construction, a full
  capture of every request/response — including any API keys, auth headers,
  or credentials that happen to flow through tool calls (e.g. a filesystem
  MCP server reading a `.env`, or a tool that echoes back an auth token).
  Confirm there's a redaction/scrub step before a tape is ever considered
  shareable — "no side effects, no tool re-execution" describes replay
  safety, not tape *content* safety.
- **Non-deterministic replay.** If a captured tool result embeds a
  timestamp, UUID, or other ambient value that the model's own response then
  echoes back, replay reproduces the *model call* deterministically but the
  overall "bug repro" may still look different session to session if
  anything downstream regenerates similar-but-not-identical values.
- **Partial/interrupted streams.** For the streaming proxies (OpenAI +
  Anthropic SSE), confirm a client disconnect or upstream error mid-stream
  leaves a well-formed, replayable partial tape rather than a truncated
  entry that hangs or throws on replay.

**Feature proposals:**
- `agent-vcr record --redact <regex|preset>` to scrub obvious secret
  shapes (bearer tokens, `sk-...`/`sk-ant-...` key prefixes) from a tape
  before it touches disk — high value given tapes are meant to be shared
  for bug repro.
- A minimal-repro command (`agent-vcr shrink tape.jsonl -o min.jsonl`) that
  trims a tape to the smallest turn range that still reproduces a given
  `agent-vcr diff`-detected divergence, since real tapes for long-running
  agents will otherwise be unwieldy to attach to an issue.

## 2. `tokenauditor` — token breakdown + waste flags

**Risk areas to check:**
- **Cache-token pricing.** Anthropic and OpenAI both charge different rates
  for cache-write vs. cache-read tokens (not just "cached vs. not"). If
  `--cost` buckets all cache tokens under one rate, cost totals will be off
  by a wide margin on any transcript that makes heavy use of prompt
  caching — exactly the users most likely to reach for a cost tool.
- **Unknown-model silence.** `--cost-json` should carry an explicit
  `model_price_unknown: true`/confidence flag whenever the heuristic
  fallback fires, so a CI job consuming the JSON doesn't treat a guessed
  number as ground truth.

**Feature proposals:**
- `tokenauditor <a.jsonl> --diff <b.jsonl>` (mirrors `agent-vcr diff`) to
  compare cost/token breakdown between two tapes of the same task — the
  natural way to answer "did my prompt change make this more expensive."
- Per-tool cost attribution (not just system/tools/messages buckets): which
  *individual* tool's results are eating the context window, to directly
  inform `toolcall-cache` denylist/allowlist decisions.

## 3. `toolcall-linter` — schema-vs-transcript linting

**Risk areas to check:**
- **JSON Schema coverage.** MCP tool schemas commonly use `oneOf`/`anyOf`/
  `$ref`/`additionalProperties`. Confirm the validator handles these rather
  than only flat `type`+`required`+`enum` — a hand-rolled validator that
  silently treats unsupported keywords as "no constraint" would produce
  false negatives on exactly the schemas most likely to have a real bug.
- **Circularity in `infer`.** The planned `toolcall-linter infer` command
  validates its own inferred schema against the same tape it was inferred
  from — that will always pass and isn't evidence the schema generalizes.
  Worth an explicit README caveat plus a note to run the inferred schema
  against a *second*, independently recorded tape before trusting it.

**Feature proposals:**
- Baseline/suppression file (`--baseline findings.json`) so a team can
  adopt the linter on an existing, imperfect transcript corpus in CI
  without a wall of preexisting findings blocking every PR.
- Per-rule severity configuration, so `--fail-on-blockers` in the shipped
  GitHub Action is actually tunable instead of a single fixed bar.

## 4. `transcript-to-test` — tape → pytest regression

**Risk areas to check:**
- **Format sniffing ambiguity.** Claude Code JSONL and hand-exported
  OpenAI-message JSON can legitimately overlap in field names once a
  transcript has been edited or partially re-serialized; confirm the
  "print a clear message and require `--format`" ambiguity path actually
  triggers rather than picking the first matching format silently.
- **Time-sensitive assertions.** A generated test that asserts on an exact
  final-answer string will be flaky if the original run's answer embedded
  wall-clock time, a run ID, or anything else not fully pinned by the
  stubbed tool outputs.

**Feature proposals:**
- `transcript-to-test batch <dir/> -o tests/` to convert a whole folder of
  recorded tapes into a suite in one pass — most users will accumulate many
  tapes, not one, especially once `agent-vcr` is in daily use.
- A `--tolerance` option for the planned `structured-match` assertion
  template, so numeric fields (cost, token counts) can assert "close to"
  rather than exact-equal against values that may shift slightly between
  pricing-table updates.

## 5. `agent-circuit-breaker` — hard spend cap + kill switch

**Risk areas to check:**
- **Check-then-act race on concurrent requests.** A hard-cap proxy that
  logs spend to SQLite *after* a request completes (unavoidable for
  streaming responses, since exact usage isn't known until the stream ends)
  has a window where several concurrent requests can all pass the
  pre-request budget check before any of them commits its spend — the cap
  can be overshot by however many requests were in flight. This directly
  contradicts the "never silently degrades" design promise and is worth
  verifying explicitly, since it's the tool's entire reason to exist.
- **Estimate vs. actual on streaming.** If the budget check is done against
  a pre-call cost estimate rather than a reservation, a request that
  *would* have blown the cap can still be dispatched if the estimate
  under-shoots actual usage.

**Feature proposals:**
- Reserve-then-reconcile accounting: hold an estimated max cost against the
  budget before dispatching a request, true it up (or release the excess)
  once the real usage is known — closes the race above.
- `agent-circuit-breaker --dry-run` / report-only mode: log what *would*
  have been blocked over a period without actually refusing requests, so
  teams can calibrate `--run-budget`/`--daily-budget` before flipping on
  hard enforcement in production.

## 6. `toolcall-cache` — content-addressed MCP result cache

**Risk areas to check:**
- **New-tool-by-default caching.** A denylist-first policy means any tool
  the cache hasn't seen before is cacheable by default until someone adds
  it to the denylist — the *first* encounter with a non-idempotent tool
  (e.g. "list open PRs", "get current weather") gets cached and can then
  serve stale, wrong data to every subsequent call, silently. This is the
  opposite failure mode from a cache miss and much more dangerous for an
  agent that trusts tool output.
- **Fuzzy-mode false hits.** Levenshtein similarity over canonicalized JSON
  args (Tier 2's `--fuzzy`) can rate two calls as "close enough" when the
  only difference is inside a large embedded text blob that materially
  changes the correct answer (e.g. "summarize this document" with one
  paragraph swapped) — worth confirming the similarity threshold is
  computed over the *whole* canonical string and not truncated.

**Feature proposals:**
- Default to an opt-*in* allowlist of known-pure tool categories (read-only
  filesystem reads, static docs/reference lookups) rather than
  denylist-by-default, since an incorrectly-served stale result is worse
  than a cache miss.
- `toolcall-cache stats --by-server` alongside the planned `--watch`, to
  see which MCP server is generating the most cache churn/hit-rate impact.

## 7. `agent-checkpoint` — save/resume via JSONL snapshot

**Risk areas to check:**
- **`merge` identity ignores turn order.** The planned merge dedupes on
  `(role, content_hash, tool_calls_hash)` — two checkpoints that share an
  early identical turn but diverge afterward could have B's later turns
  spliced into the middle of A's sequence rather than the merge detecting
  and reporting a branch point. Worth an explicit test with two checkpoints
  that share a prefix and then diverge.
- **Silent no-op resume.** `AGENT_CHECKPOINT_INIT` is a convention each
  agent framework has to independently honor; there's no documented
  handshake confirming a given resume actually took effect, so an agent
  that doesn't fully support the convention could "resume" by just
  starting fresh, with no error surfaced.

**Feature proposals:**
- `agent-checkpoint verify <checkpoint.jsonl>` to check for a
  resumed-marker/consumption signal after a run claims to have resumed —
  closes the silent-no-op gap above.
- `--squash-before <turn>` compaction for long-running agents whose
  checkpoint file otherwise grows without bound.

## 8. `transcript-bridge` — provider format conversion

**Risk areas to check:**
- **Multi-hop loss accumulation.** "Reports loss instead of silently
  dropping" is checked per hop; a round trip (Claude → canonical → OpenAI →
  canonical → Claude) can still accumulate semantic drift even when each
  individual hop reports zero loss, if the canonical shape loses precision
  in aggregate. Worth a two-hop (not just one-hop) self-check.
- **Gemini's multi-part turns.** Gemini's `contents`/`parts` model allows
  multiple function calls and function responses within a single turn;
  if the canonical tape format (built around Claude/OpenAI's more
  single-call-per-message shape) doesn't have a slot for that, a multi-part
  Gemini turn could flatten into one part — which is exactly the kind of
  loss the tool is designed to report, so it needs its own explicit test,
  not just the synthetic single-call fixtures.

**Feature proposals:**
- `transcript-bridge roundtrip <file> --via canonical` — a self-test any
  user can run against their *own* real transcripts (not just the shipped
  synthetic fixtures) before trusting a migration.
- `--loss-budget N`: fail only if loss exceeds N fields, as a middle ground
  between "allow silently" and `--strict`'s all-or-nothing.

## 9. `mcp-openai-bridge` — MCP servers as OpenAI function-calling tools

**Risk areas to check:**
- **Namespace collisions in multi-server mode.** Tools are namespaced
  `server_id__tool_name`; if `--server-id` is omitted for two servers, both
  default to a generated ID pattern (e.g. `stdio-1`) — worth confirming the
  auto-numbering actually increments per-server-type rather than colliding,
  and that a genuine name collision fails loudly at startup instead of
  silently shadowing one server's tool with another's.
- **OpenAI strict-mode schema incompatibility.** MCP tool schemas can use
  JSON Schema features (bare `$ref`, missing `additionalProperties: false`)
  that OpenAI's function-calling strict mode rejects outright — a call
  would fail at the OpenAI API layer with an opaque schema error rather
  than a clear message from the bridge identifying which tool isn't
  strict-mode-compatible.

**Feature proposals:**
- `mcp2openai validate --config mcp-servers.json`: a dry-run compatibility
  check that lists which MCP tools will/won't survive translation to
  OpenAI strict function-calling schemas, before wiring it into a live
  agent loop.
- Fail-fast startup-time collision detection for the `server_id__tool_name`
  namespace, with a clear error naming both colliding servers.

## 10. `prompt-portability-linter` — vendor-lock scanner

**Risk areas to check:**
- **Score floor.** Confirm the planned `--score` formula clamps at 0
  (`max(0, 100 - deductions)`) — a prompt with many findings should read
  as "very unportable," not produce a nonsensical negative number.
- **Structural false-negative risk.** The linter is fundamentally a
  snapshot of each provider's *known* vendor-lock surface at ruleset
  authoring time. Providers ship new proprietary request fields
  continuously; a prompt using a brand-new vendor-specific feature will
  score falsely "100/100 portable" until a rule is added for it. A clean
  bill of health from this tool is a weaker signal than it looks — worth
  being explicit about that in the README, since a false "portable" is
  worse than no answer.

**Feature proposals:**
- Print the `rules.yaml` version/last-updated date alongside every report
  (and optionally warn if it's stale past N days), so a 100/100 score
  carries a visible freshness caveat instead of reading as absolute truth.
- An "unclassified" heuristic mode: flag any top-level request
  field/parameter *not* on a known portable-core allowlist as
  `possible-vendor-lock (unclassified)`, trading some false positives for
  catching genuinely new lock-in before an explicit rule exists for it.

## Suggested priority order

1. **Umbrella fixes (done this session)** — already applied and verified;
   review/merge.
2. **`agent-circuit-breaker`'s check-then-act race** — the tool's whole job
   is a *hard* cap; if it can be overshot under concurrency that undercuts
   the core value proposition more than any other finding here.
3. **`toolcall-cache`'s cache-by-default-until-denylisted posture** — same
   shape of problem (silent wrong data beats loud failure) for a tool meant
   to sit transparently in the middle of every tool call.
4. **`tokenauditor`'s cache-token pricing** — directly affects the accuracy
   of the numbers the whole `--cost` feature exists to produce.
5. Everything else — genuine quality-of-life and defense-in-depth
   improvements, not "this tool doesn't do what it says" findings.

Add a `.github/workflows/selfcheck.yml` to this umbrella repo as a
standalone, cheap first step — it would have caught bug #1 above
automatically instead of needing someone to run `selfcheck.py` by hand on
Linux.
